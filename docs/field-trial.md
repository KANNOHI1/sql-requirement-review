# 会社環境での初回試行

会社の Gemini CLI で、実際の要件と SQL にこの Skill を 1 本使ってみる手順。**すべて会社の VM の中で完結する。** 結果を Skill の管理元（このリポジトリ）に戻す必要はない。Skill 自体の文言を直したい時だけ、表名・数値を含まない要約（罠 ID・判定・理由の構造）を任意で伝える。

## 1. 会社側で貼る指示文

前提: `README.md` の「配置（Gemini CLI）」どおりに Skill を置き（`skill/` を丸ごとコピーするので `references/` と `scripts/` も一緒に入る）、clone は消してある。レビュー作業はこのリポジトリの clone とは無関係の作業ディレクトリ（例: `~/sql-review/`）で行い、そこに要件と SQL を 1 ファイル（例: `req01.md`）にまとめてある。「保存して」で書かれるファイルは VM の中に留まる。危ないのは保存先が git 管理下にある場合だけなので、作業ディレクトリを git の外に置くことで塞ぐ。`references/metric-definitions.md` は会社側で記入する。

```
@req01.md を sql-requirement-review スキルでレビューして。判定票も付けて、req01_result.md に保存して。
```

判定票の形式は Skill 内の `references/verdict-sheet.md` にあり、Gemini がそれを読んでレビュー結果の末尾（`---VERDICT---` 以降）に書く。`req01_result.md` が会社側の成果物で、ズレ一覧を読み、確認質問をエンジニアに送るために使う。

**会社の VM に個人の GitHub 認証情報（トークン、`gh auth login`、git の credential）を置かない。** 公開リポジトリの clone に認証は要らず、push には要る。置かなければ Gemini CLI は物理的にこのリポジトリへ書けない。これが実質的な保証で、以下の Skill の文言・.gitignore・clone の削除はその上の保険にすぎない。

**Skill の導入（clone・コピー）も Gemini にやらせない。JupyterLab のターミナルで自分で打つ。** 2026-09-29 の試行で、Gemini に clone を頼んだところ URL の綴り違い（`requirment`）で clone に失敗し、Gemini はそれを認証の問題と誤解して `gh auth status`・`git config --list`・`ssh -T git@github.com` と認証情報を探し始めた。しかも YOLO モード（確認なしで実行）が ON だった。**YOLO モードは使わない**（Ctrl+Y で OFF）。OFF ならシェル実行のたびに確認が出る。

**Gemini に git push・アップロード・送信を指示しない**（Skill 側でも拒否するよう書いてあるが、LLM への指示は破られうる）。会社の VM から外へ出す操作を AI にやらせると、目視確認を飛ばした非公式の持ち出し経路になる。

## 付録 2: 不明だった定義をデータとメタデータで確定させるプロンプト（コスト制約付き）

エージェントが BigQuery に SQL を実行できる前提。原則は 3 つ: メタデータで済むことはデータを読まない（INFORMATION_SCHEMA と列の説明文は課金スキャンにならない）／読むなら 1 パーティション・必要な列だけ（LIMIT は読む量を減らさない）／実行前に dry run で読む量を出し、上限超えは実行せず報告。「確定」の行だけ用語集の追記案にし、「推定」は根拠付きの仮説としてエンジニアへ。税は参照列が金額 1 本しか無ければデータからは決まらない。

```
「売上」の定義で不明だった 3 点（税・返品/訂正・日付の基準）を、データとメタデータから確定したい。次の順で進め、各段階の結論を短く報告して。英語での再説明・思考の経過・言い直しは出さない（トークンを使わない）。

■ コストの規則（例外なし）
- SELECT * を使わない。必要な列だけ SELECT する
- データを読むクエリは、必ずパーティション列（日付）を 1 日に絞る。直近の 1 日でよい
- LIMIT は読む量を減らさないので、絞り込みの代わりに使わない
- 実行前に必ず dry run で読む量（バイト）を出し、1 GB を超えるなら実行せず「このクエリは N GB のため未実行」と報告して次へ進む
- 同じ表のコンテキスト取得を繰り返さない。既に取得したスキーマを使う
- 各段階で分かったことは、次の段階の判断にだけ使い、同じことを二度調べない

■ 段階 1: メタデータだけで答える（データを読まない）
取引ビューとその元表について、INFORMATION_SCHEMA（COLUMNS / COLUMN_FIELD_PATHS / PARTITIONS / TABLE_OPTIONS）と列の説明文から次を答えて。
1-1. 金額に関する列をすべて列挙（列名・型・説明文）。税込・税抜・税額・値引・単価・数量に当たる列があるか
1-2. 返品・訂正・取消を示す列があるか（区分・フラグ・マイナス許容の説明など）
1-3. 日付・時刻に関する列をすべて列挙（列名・型・説明文）。TIMESTAMP 型の列があるか。パーティション列はどれか
1-4. 取引を一意にする ID 列があるか
1-5. 表のサイズ（バイト・行数）と、直近のパーティション日付。**必ず INFORMATION_SCHEMA.PARTITIONS または TABLES から取る。MAX(日付列) を表に対して実行しない（それは全列スキャン）。** 対象がビューなら、まず元表を特定してその INFORMATION_SCHEMA を見る
1-6. 元表がパーティション分割されているか、分割列は何か、ビュー経由で刈り込みが効くか（dry run で「1 日に絞った時の読む量」と「絞らない時の読む量」を比べて報告。実行はしない）
ここまでで税・返品・日付の 3 点が説明文から確定するなら、段階 2 は飛ばして「段階 1 で確定」と報告して。

■ 段階 2: 直近 1 日だけ読んで確かめる（段階 1 で決まらなかった項目だけ）
各クエリは dry run → 読む量を報告 → 1 GB 未満なら実行。結果は件数と比率だけ返す（生の行は返さない）。
2-1. 税: 税込と税抜の両方の列があるなら、その 1 日で SUM(税込) / SUM(税抜) を出す（1.08〜1.10 なら税込・税抜の関係が確定）。単価×数量の列があるなら SUM(金額) / SUM(単価×数量) を出す。参照できる列が金額 1 本しか無ければ「データだけでは判別不能。エンジニアに確認」と書く
2-2. 返品: その 1 日で、金額 < 0 の行数と数量 < 0 の行数、全行数。返品フラグ列があればフラグ別の行数。マイナス行があれば「返品はマイナス行として混在」、無ければ「この 1 日にはマイナス行なし（返品の表現は未確定）」
2-3. 日付の基準: 時刻列があれば、その 1 日の時間帯別（0〜23 時）の行数。ピークが 10〜20 時なら JST、1〜11 時なら UTC の疑い。時刻列が無く DATE 型だけなら「DATE の生成時のタイムゾーンは ETL 側の情報が必要」と書く
2-4. 重複: ID 列があれば、その 1 日の COUNT(*) と COUNT(DISTINCT ID)

■ 報告の形式（この表だけ。前置き・後書き不要）
| 項目 | 結論 | 根拠（段階・クエリの要旨・読んだ量） | 確度（確定／推定／判別不能） |
|---|---|---|---|
| 税 | | | |
| 返品・訂正 | | | |
| 日付の基準列 | | | |
| タイムゾーン | | | |
| 取引の重複 | | | |
最後に、実行したクエリの本数と合計で読んだ量を 1 行。
```

この環境の外に出すなら、表の「結論」と「確度」の列だけ（任意）。列名・件数は出さない。

2026-09-29 の実行結果（要約）: 税＝判別不能（金額列 1 本のみ）、返品＝推定（フラグなし・単純合計）、日付列＝確定、タイムゾーン＝推定 JST、重複＝レシート ID は複数列の組合せで確定。**エージェントは「1 日分でも上限超過」と言いながら MAX(日付列) を絞り込みなしで実行した（自己申告で約 138 GB の全列スキャン）。** 原因は当時のプロンプトが 1-5 の取り方を指定していなかったこと。上の 1-5・1-6 はその修正。もう 1 つの発見: 1 日に絞っても上限超過＝パーティション刈り込みが効いていない疑い。エージェントの 1 問あたりのスキャン量に直結するため、エンジニアへの質問に加えた。
