# 会社環境での試行手順と持ち帰り票

会社の Gemini CLI で、実際の要件と SQL にこの Skill を使い、**会社のデータを一切持ち出さずに**、Skill の効き具合だけを持ち帰るための手順。持ち帰ってよいのは「罠 ID・判定・構造の言葉で書いた理由・件数」だけ。要件文・SQL・表名・列名・得意先名・商品名・金額は持ち帰らない。

## 1. 会社側で貼る指示文

前提: `README.md` の「配置（Gemini CLI）」どおりに Skill を置き（`skill/` を丸ごとコピーするので `references/carry-sheet.md` も一緒に入る）、clone は消してある。レビュー作業はこのリポジトリの clone とは無関係の作業ディレクトリ（例: `~/sql-review/`）で行い、そこに要件と SQL を 1 ファイル（例: `req01.md`）にまとめてある。「保存して」で書かれるファイルは VM の中に留まる。危ないのは保存先が git 管理下にある場合だけなので、作業ディレクトリを git の外に置くことで塞ぐ。`references/metric-definitions.md` は会社側で記入する（記入内容は会社の外に出さない）。

```
@req01.md を sql-requirement-review スキルでレビューして。結果は req01_result.md に、持ち帰り票は req01_carry.md に保存して。
```

持ち帰り票の規則と形式は Skill 内の `references/carry-sheet.md` にあり、Gemini がそれを読んで書く。`req01_result.md` はレビュー結果そのもので、会社側の成果物（ズレ一覧を読み、確認質問をエンジニアに送るために使う）。会社の外に出さない。持ち帰るのは `req01_carry.md` の内容だけ。持ち帰る前に、票の中に表名・数字が混ざっていないか目で確認する。

**会社の VM に個人の GitHub 認証情報（トークン、`gh auth login`、git の credential）を置かない。** 公開リポジトリの clone に認証は要らず、push には要る。置かなければ Gemini CLI は物理的にこのリポジトリへ書けない。これが実質的な保証で、以下の Skill の文言・.gitignore・clone の削除はその上の保険にすぎない。

**Skill の導入（clone・コピー）も Gemini にやらせない。JupyterLab のターミナルで自分で打つ。** 2026-09-29 の試行で、Gemini に clone を頼んだところ URL の綴り違い（`requirment`）で clone に失敗し、Gemini はそれを認証の問題と誤解して `gh auth status`・`git config --list`・`ssh -T git@github.com` と認証情報を探し始めた。しかも YOLO モード（確認なしで実行）が ON だった。**YOLO モードは使わない**（Ctrl+Y で OFF）。OFF ならシェル実行のたびに確認が出る。

**Gemini に git push・アップロード・送信を指示しない**（Skill 側でも拒否するよう書いてあるが、LLM への指示は破られうる）。会社の VM から外へ出す操作を AI にやらせると、目視確認を飛ばした非公式の持ち出し経路になる。持ち帰りは目視確認の後、菅野さんが自分の手で、会社の規則に従った経路で行う。

## 2. エンジニアと話した後に手で足す欄

`req01_carry.md` の末尾に「エンジニアの判断（利用者が手で記入）」の欄が空欄で出力される。エンジニアと話した後、菅野さんが手で埋める。ここが正解ラベルになる。エンジニアの同意なしに「合っていた」とは記録しない。

## 3. 持ち帰った後の処理（このリポジトリ側）

1. 持ち帰り票のうち、**「該当なし」の行は転記しない**。転記するのは、判定・実行確認・定義の入手、該当と不明の行（T の ID と理由）、要確認の理由、数値の 4 行、エンジニアの判断欄。全文なら約 1,300 字、この規則で約 500 字（架空データでの実測）。この内容を作業セッションに貼れば、下の「試行の記録」への転記とチェックリストの修正はこちらで行う
2. 下の「試行の記録」に 1 行足す。実物ファイル（`req01_*.md`）はリポジトリに入れない
3. 不同意の T・見逃しがあれば、`skill/references/trap-checklist.md` の該当項目の「見つけ方」か「注」を書き換える。「T に無い」見逃しは、新しい罠項目の候補として `docs/STATUS.md` の未解決に足す
4. 可能なら、同じ構造のズレを `tests/datasets.sql` の架空データで再現するテストケース（罠なら C、正しい SQL なら K）を `tests/cases.yaml` に足し、ブラインド評価にかける
5. 「定義表が空で止まった指標の数」が多ければ、それは Skill ではなく `metric-definitions.md` の記入不足。会社側で行を埋める
6. `/save` で STATUS と journal を更新する

## 付録: SQL 生成エージェントに定義の所在を聞くプロンプト（[U-0929-07]）

エージェントの自己申告は間違いうるので、根拠の所在を言わせ、分からなければ「不明」と言わせる。回答はエンジニアに裏取りしてから使う。エージェントの申告と用語集の実物が食い違えば、それ自体が持ち帰る事実（表名・数値は持ち帰らない）。

```
あなたの設定と挙動について確認したい。推測で埋めず、根拠が示せないものは「不明」と答えて。

1. 営業の言葉（例: 売上・販売数量・目標達成率・前年比）の定義を、あなたはどこから得ている？
   次のどれか、複数なら全部: システムプロンプトに直接書かれている／用語集（別ファイル・別設定）／BigQuery のテーブルや列の説明文／その他（具体的に）／どこにも無く、SQL を書くたびに推定している

2. 「売上」について、いま使っている定義をこの表の形で書いて。分からない欄は「不明」。
   | 指標名 | 対応する表.列 または 計算式 | 税（税込/税抜） | 返品・訂正（差し引く/含めない） | 日付の基準（列名・JST か UTC か） | この定義の出所 |

3. 同じ表の形で、あなたが定義を持っている指標をすべて列挙して。

4. 要件に出てきた言葉が用語集に無いとき、あなたはどうする？（推定して SQL を書く／利用者に聞く／その他）。直近でそうなった例があれば挙げて。

5. あなたの定義の出所は、他の得意先向けエージェントと共通の場所か、あなた専用の設定か。分かる範囲で答えて。
```

追加の問い（1 回目の回答で「売上」の税・返品・日付基準が不明だった時）:

```
6. 「売上」を集計する SQL を書くとき、税（税込/税抜）、返品・訂正行の扱い、期間の基準（どの日付列か、JST か UTC か）は何で決めている？ システムプロンプトの「集計の基本ルール」に書かれているなら、その要旨を。書かれていないなら「推定している」と答えて。
```

見るポイント: 問 2 の「出所」欄が埋まるか（埋まらなければ定義は暗黙）／問 3 の指標の数（用語集の実際の厚み）／問 4 で「推定して書く」なら、それが T09・T13 の発生源。問 3 の表は `metric-definitions.md` と同じ列なので、エンジニアが正しいと認めた行だけを VM の表に写す。

## 付録 2: 不明だった定義をデータとメタデータで確定させるプロンプト（コスト制約付き）

エージェントが BigQuery に SQL を実行できる前提。原則は 3 つ: メタデータで済むことはデータを読まない（INFORMATION_SCHEMA と列の説明文は課金スキャンにならない）／読むなら 1 パーティション・必要な列だけ（LIMIT は読む量を減らさない）／実行前に dry run で読む量を出し、上限超えは実行せず報告。「確定」の行だけ用語集の追記案にし、「推定」は根拠付きの仮説としてエンジニアへ。税は参照列が金額 1 本しか無ければデータからは決まらない。

```
「売上」の定義で不明だった 3 点（税・返品/訂正・日付の基準）を、データとメタデータから確定したい。次の順で進め、各段階の結論を短く報告して。英語での再説明・思考の経過・言い直しは出さない（トークンを使わない）。

■ コストの規則（例外なし）
- SELECT * を使わない。必要な列だけ SELECT する
- データを読むクエリは、必ずパーティション列（日付）を 1 日に絞る。直近の 1 日でよい
- LIMIT は読む量を減らさないので、絞り込みの代わりに使わない
- 実行前に必ず dry run で読む量（バイト）を出し、1 GB を超えるなら実行せず「このクエリは N GB のため未実行」と報告して次へ進む
- 同じ表のコンテキスト取得を繰り返さない。既に取得したスキーマを使う
- 各段階で分かったことは、次の段階の判断にだけ使い、同じことを二度調べない

■ 段階 1: メタデータだけで答える（データを読まない）
取引ビューとその元表について、INFORMATION_SCHEMA（COLUMNS / COLUMN_FIELD_PATHS / PARTITIONS / TABLE_OPTIONS）と列の説明文から次を答えて。
1-1. 金額に関する列をすべて列挙（列名・型・説明文）。税込・税抜・税額・値引・単価・数量に当たる列があるか
1-2. 返品・訂正・取消を示す列があるか（区分・フラグ・マイナス許容の説明など）
1-3. 日付・時刻に関する列をすべて列挙（列名・型・説明文）。TIMESTAMP 型の列があるか。パーティション列はどれか
1-4. 取引を一意にする ID 列があるか
1-5. 表のサイズ（バイト・行数）と、直近のパーティション日付。**必ず INFORMATION_SCHEMA.PARTITIONS または TABLES から取る。MAX(日付列) を表に対して実行しない（それは全列スキャン）。** 対象がビューなら、まず元表を特定してその INFORMATION_SCHEMA を見る
1-6. 元表がパーティション分割されているか、分割列は何か、ビュー経由で刈り込みが効くか（dry run で「1 日に絞った時の読む量」と「絞らない時の読む量」を比べて報告。実行はしない）
ここまでで税・返品・日付の 3 点が説明文から確定するなら、段階 2 は飛ばして「段階 1 で確定」と報告して。

■ 段階 2: 直近 1 日だけ読んで確かめる（段階 1 で決まらなかった項目だけ）
各クエリは dry run → 読む量を報告 → 1 GB 未満なら実行。結果は件数と比率だけ返す（生の行は返さない）。
2-1. 税: 税込と税抜の両方の列があるなら、その 1 日で SUM(税込) / SUM(税抜) を出す（1.08〜1.10 なら税込・税抜の関係が確定）。単価×数量の列があるなら SUM(金額) / SUM(単価×数量) を出す。参照できる列が金額 1 本しか無ければ「データだけでは判別不能。エンジニアに確認」と書く
2-2. 返品: その 1 日で、金額 < 0 の行数と数量 < 0 の行数、全行数。返品フラグ列があればフラグ別の行数。マイナス行があれば「返品はマイナス行として混在」、無ければ「この 1 日にはマイナス行なし（返品の表現は未確定）」
2-3. 日付の基準: 時刻列があれば、その 1 日の時間帯別（0〜23 時）の行数。ピークが 10〜20 時なら JST、1〜11 時なら UTC の疑い。時刻列が無く DATE 型だけなら「DATE の生成時のタイムゾーンは ETL 側の情報が必要」と書く
2-4. 重複: ID 列があれば、その 1 日の COUNT(*) と COUNT(DISTINCT ID)

■ 報告の形式（この表だけ。前置き・後書き不要）
| 項目 | 結論 | 根拠（段階・クエリの要旨・読んだ量） | 確度（確定／推定／判別不能） |
|---|---|---|---|
| 税 | | | |
| 返品・訂正 | | | |
| 日付の基準列 | | | |
| タイムゾーン | | | |
| 取引の重複 | | | |
最後に、実行したクエリの本数と合計で読んだ量を 1 行。
```

持ち帰るのは表の「結論」と「確度」の列だけ。列名・件数は持ち帰らない。

2026-09-29 の実行結果（要約）: 税＝判別不能（金額列 1 本のみ）、返品＝推定（フラグなし・単純合計）、日付列＝確定、タイムゾーン＝推定 JST、重複＝レシート ID は複数列の組合せで確定。**エージェントは「1 日分でも上限超過」と言いながら MAX(日付列) を絞り込みなしで実行した（自己申告で約 138 GB の全列スキャン）。** 原因は当時のプロンプトが 1-5 の取り方を指定していなかったこと。上の 1-5・1-6 はその修正。もう 1 つの発見: 1 日に絞っても上限超過＝パーティション刈り込みが効いていない疑い。エージェントの 1 問あたりのスキャン量に直結するため、エンジニアへの質問に加えた。
