# 会社環境での試行手順と持ち帰り票

会社の Gemini CLI で、実際の要件と SQL にこの Skill を使い、**会社のデータを一切持ち出さずに**、Skill の効き具合だけを持ち帰るための手順。持ち帰ってよいのは「罠 ID・判定・構造の言葉で書いた理由・件数」だけ。要件文・SQL・表名・列名・得意先名・商品名・金額は持ち帰らない。

## 1. 会社側で貼る指示文

前提: `README.md` の「配置（Gemini CLI）」どおりに Skill を置き（`skill/` を丸ごとコピーするので `references/carry-sheet.md` も一緒に入る）、clone は消してある。レビュー作業はこのリポジトリの clone とは無関係の作業ディレクトリ（例: `~/sql-review/`）で行い、そこに要件と SQL を 1 ファイル（例: `req01.md`）にまとめてある。「保存して」で書かれるファイルは VM の中に留まる。危ないのは保存先が git 管理下にある場合だけなので、作業ディレクトリを git の外に置くことで塞ぐ。`references/metric-definitions.md` は会社側で記入する（記入内容は会社の外に出さない）。

```
@req01.md を sql-requirement-review スキルでレビューして。結果は req01_result.md に、持ち帰り票は req01_carry.md に保存して。
```

持ち帰り票の規則と形式は Skill 内の `references/carry-sheet.md` にあり、Gemini がそれを読んで書く。`req01_result.md` はレビュー結果そのもので、会社の外に出さない。持ち帰るのは `req01_carry.md` の内容だけ。持ち帰る前に、票の中に表名・数字が混ざっていないか目で確認する。

**Gemini に git push・アップロード・送信を指示しない**（Skill 側でも拒否するよう書いてある）。会社の VM から外へ出す操作を AI にやらせると、目視確認を飛ばした非公式の持ち出し経路になる。持ち帰りは目視確認の後、菅野さんが自分の手で、会社の規則に従った経路で行う。

## 2. エンジニアと話した後に手で足す欄

`req01_carry.md` の末尾に「エンジニアの判断（利用者が手で記入）」の欄が空欄で出力される。エンジニアと話した後、菅野さんが手で埋める。ここが正解ラベルになる。エンジニアの同意なしに「合っていた」とは記録しない。

## 3. 持ち帰った後の処理（このリポジトリ側）

1. 下の「試行の記録」に 1 行足す。実物ファイル（`req01_*.md`）はリポジトリに入れない
2. 不同意の T・見逃しがあれば、`skill/references/trap-checklist.md` の該当項目の「見つけ方」か「注」を書き換える。「T に無い」見逃しは、新しい罠項目の候補として `docs/STATUS.md` の未解決に足す
3. 可能なら、同じ構造のズレを `tests/datasets.sql` の架空データで再現するテストケース（罠なら C、正しい SQL なら K）を `tests/cases.yaml` に足し、ブラインド評価にかける
4. 「定義表が空で止まった指標の数」が多ければ、それは Skill ではなく `metric-definitions.md` の記入不足。会社側で行を埋める
5. `/save` で STATUS と journal を更新する
