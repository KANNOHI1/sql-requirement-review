# sql-requirement-review の解説（非エンジニア向け）

## これは何か

営業の質問（「6 月の得意先別の売上を知りたい」）に対して、エンジニアや AI エージェントが書いた SQL が**本当にその質問に答えているか**を判定する、Gemini CLI 用の手順書一式です。SQL が動くかどうかは見ません。「動くけれど数字が違う」を見つけるためのものです。

Alteryx でいえば、他人が作ったワークフローを開いて「このフィルターは先月の分を落としていないか」「この結合で行が増えていないか」を順に点検する作業を、Gemini に代わりにやらせるマクロです。

## しないこと

- SQL を書き直さない。直し方の方向は書くが、修正版の SQL を作るのは人かエージェントの仕事
- データを勝手に読まない。`bq` が使える環境でも、読むのは確認のための件数だけで、上限（10 GB）を超えたら止まる。書き換える命令（INSERT や DELETE）は絶対に実行しない
- 結果をどこにも送らない。ファイルに書いて終わる。「GitHub に上げて」と言われても断る

## 中身（フォルダの構成）

| ファイル | 役割 | Alteryx でいえば |
|---|---|---|
| `SKILL.md` | 手順そのもの。Gemini はこれを読んで動く | マクロの本体 |
| `references/trap-checklist.md` | 罠 15 項目。「どこを見ると見つかるか」「Alteryx でいうと何か」「放っておくとどう間違うか」 | 点検リスト |
| `references/metric-definitions.md` | 「売上＝どの列、税込か、返品は引くか」の正解表。使う環境で記入する | マクロの設定シート |
| `references/verdict-sheet.md` | 判定票。集計しやすい固定形式 | 処理ログの様式 |
| `references/batch-review.md` | ログを一括でレビューする時の手順 | バッチ実行の手順書 |
| `scripts/` | 一括レビュー用のプログラム 3 本（分解・判定・集計） | バッチ用のワークフロー |

## 挙動（1 本の SQL をレビューする時に何が起きるか）

Gemini は次の 6 段階を順に踏み、決まった見出しで結果を書きます。

1. **要件の分解**。営業の質問を 6 つの要素に分けます。対象（どの得意先・商品）、期間（いつからいつまで、JST か）、指標の定義（売上とは何か）、粒度（1 行が何を表すか）、絞り込み（除外条件）、比較軸（前年比・上位 N 件）。質問に書いていない要素は「指定なし」とし、勝手に埋めません。
2. **SQL の逆翻訳**。SQL を実行される順に日本語へ読み下します。各部分に Alteryx のツール名を添えます（FROM＝入力データ、JOIN＝結合、WHERE＝集計前フィルター、GROUP BY＝集計、HAVING＝集計後フィルター、SELECT の式＝フォーミュラ、ORDER BY / LIMIT＝並べ替え／サンプル）。最初に、SQL が使っている表と列がテーブル定義に実在するかを 1 つずつ照合します。最後に「この SQL が実際に答えている質問」を 1 文で書きます。ここは要件を見ずに SQL だけから書かせます。要件に引きずられた読み方を防ぐためです。
3. **突き合わせ**。1 の要件と 2 の実際を、6 要素ごとに表で比べ、一致／不一致／不明を付けます。
4. **罠チェック**。15 項目を全部点検し、該当・該当なし・不明のどれかを必ず書きます。「構造上起こりうるなら該当」が基準です。データを見なくても、SQL の書き方と表の定義から「行が増えうる」「NULL の行が消えうる」と示せれば該当にします。
5. **実行確認（任意）**。`bq` が使える時だけ、件数の比較などの読み取りだけを行います。使えなければ「読解のみ（未実行）」と明記して飛ばします。
6. **判定**。3 段階です。

| 判定 | 意味 |
|---|---|
| 不一致 | 数字か返ってくる行が変わるズレが 1 つ以上ある。根拠（SQL のどの行で、何がどうずれるか）を示せている |
| 要確認 | 決定的なズレは無いが、要件が曖昧・定義が無い・列の型が不明などで言い切れない |
| 合致 | 6 要素が全部一致し、罠が全部該当なし |

「疑わしいだけで不一致にしない」が規則です。根拠を示せないものは要確認に回します。正しい SQL を不一致と言うのも、見逃しと同じ失敗として扱っています。

出力は上から、判定と理由 1 行、ズレ一覧（重大度と直し方の方向）、エンジニアへの確認質問（そのまま送れる文面）、突き合わせ表、罠チェック、読み下し、実行確認の順です。**普段読むのは上の 3 つ**です。残りは根拠を確かめたい時に見ます。

## 罠 15 項目（放っておくとどう間違うか）

| ID | 何が起きるか |
|---|---|
| T01 | 結合で行が増え、売上が 2 倍 3 倍に膨らむ |
| T02 | 実績ゼロの得意先が一覧から消え、「全店達成」に見える |
| T03 | 「関東以外」の集計から、地域が未登録の得意先が黙って消える |
| T04 | 「購入店舗数」のつもりが取引件数になり、数倍になる |
| T05 | 「合計 5 万円以上の得意先」が「1 回 5 万円以上の取引の合計」になる |
| T06 | 時差の扱いが無く、月初 0 時台の売上が前月に入る |
| T07 | 月末 1 日分が抜ける。「先月」が「過去 30 日」になる |
| T08 | 返品を引かずに売上を過大に出す |
| T09 | 定価で売上を出して値引き分だけ過大になる。税込と税抜の取り違え |
| T10 | 在庫が日数分合算されて何倍にもなる |
| T11 | 全体達成率が、得意先ごとの達成率の単純平均になっている |
| T12 | 実行のたびに違う「トップ 5」が出る。下位 5 件が出る |
| T13 | 似た名前の別の表・別の列を使っていて、論理は正しいのに数字が全部違う |
| T14 | 元データに同じ取引が重複して入っていて、数字が実際より大きい |
| T15 | 得意先名の表記ゆれで一部が漏れる。部分一致で別の得意先まで拾う |

## 使い方 A: SQL を 1 本レビューする

1. 作業用のフォルダ（例: `~/sql-review/`）に `req01.md` を作り、営業の質問と SQL を書く。テーブル定義があれば添える。

```
# 要件
営業の質問をそのまま

# SQL
レビューしたい SQL をそのまま貼る

# テーブル定義
（あれば。無ければこの節ごと省く）
```

2. そのフォルダで Gemini CLI を起動し、1 行貼る。

```
@req01.md を sql-requirement-review スキルでレビューして。判定票も付けて、req01_result.md に保存して。
```

3. `req01_result.md` の上 3 つ（判定・ズレ一覧・確認質問）を読む。確認質問はそのままエンジニアに送れる文面になっている。
4. エンジニアと話した後、ファイル末尾の「エンジニアの判断」欄を手で埋める。ここが正解ラベルになり、Skill の当たり外れを後で測れる。

## 使い方 B: エージェントのログを一括でレビューする

エージェントの利用ログ（xlsx。誰がいつ何を聞き、どんな SQL が生成されたか）を、1 行ずつ上のレビューにかけ、「どこを直せば何件減るか」を出します。Gemini に xlsx を直接読ませません。行の切れ目や複数 SQL の解釈を LLM にやらせると壊れるので、プログラムで 1 件ずつに分解します。

```bash
pip install pandas openpyxl
S=~/.gemini/skills/sql-requirement-review/scripts
python $S/split_log.py --xlsx log.xlsx --out work/ --schema schema.md   # A. 分解
bash $S/run_reviews.sh work/ 10                                          # B. まず 10 件
bash $S/run_reviews.sh work/                                             # B. 残り全部（途中で止めても再開できる）
python $S/aggregate.py work/                                             # C. 集計
```

- A は、同じ会話の前の質問を「文脈」として付けます。「それを店舗別で」のような短い質問は、前の質問が無いと何の話か分からないためです。1 行に複数の SQL があれば最後の 1 本を対象にします。エージェントの回答文は入れません（レビューが回答に引きずられるため）
- B は、Gemini を 1 件ごとに別々に起動します。1 回の会話に全部入れると文脈が溢れて精度が落ちるためです。Gemini にファイルを書かせず、出力をそのまま保存します
- C の `summary.md` で見るのは 3 つ。**判定の分布**（不一致の割合）、**直す場所ごとの件数**（用語集・スキーマの説明文・日付ルール・要件の解釈ルール・表の構造・NULL と文字列。件数が多い場所から直す）、**人の正誤判定との突き合わせ**（人と Skill が食い違った行を先に読む）

## 気をつけること

- **指標の定義表を埋める。** 空欄のままでも動くが、その指標は「定義なし」として毎回確認質問に回る。用語集やエージェントの設定に定義があるなら、そこから写す。二重管理はしない
- **作業フォルダを git の外に置く。** 要件と SQL と結果は、Skill を取ってきた clone の中に置かない
- **Gemini に git や導入作業をさせない。** 導入はターミナルで自分で打つ。YOLO モード（確認なしで実行）は切る
- **`bq` を使うなら上限を守らせる。** Skill には書いてあるが、LLM への指示は破られうる。数字が大きい表では実行確認を切る（「読解のみ」で十分判定できる）
- **正しい SQL も流す。** 罠がある SQL だけを見せると、Skill の「誤検出しない力」が測れない
